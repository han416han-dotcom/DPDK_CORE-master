# Auto Scan 与 CoreDump 解析逻辑分析

## 1. 当前系统的根本逻辑

从现有代码看，这套系统的主链路已经比较清晰：

1. 文件进入系统
   - 手工上传
   - 自动扫描目录发现新文件
2. 文件入库
   - `CoredumpFile` / `LogFile` 保存文件元信息、状态、路径、哈希
3. 异步解析
   - `DataParserService` 根据配置的解析后端调用对应解析器
   - 当前统一走 `WSL2_GDB`
4. 特征归一化
   - `DataNormalizationService` 把 GDB 输出、日志输出整理成 `ParsedFeature`
5. 后续 AI 诊断与可视化
   - 基于 `ParsedFeature` 做案例匹配、根因分析和前端展示

也就是说，这不是单纯的上传工具，而是在逐步形成一个“自动采集 + 自动解析 + 自动归因 + 可视化展示”的平台。

---

## 2. 当前三大目标的合理分层

### 第一层：自动抓取与自动解析
- 自动发现新增 core/log 文件
- 自动识别对应程序 ELF
- 自动调用 gdb 解析
- 自动落结构化特征

### 第二层：AI 辅助根因分析
- 基于调用栈、异常信号、日志关键词、线程信息做异常模式识别
- 做案例库匹配
- 输出疑似根因和排查建议

### 第三层：可视化展示
- 调用栈图谱
- 线程关系图
- 时间线
- 关键问题节点高亮
- 诊断卡片式输出

目前最该优先打稳的是第一层。

## 3. 当前真实运行场景

结合现有配置，当前测试环境是：

- 测试文件位于 WSL2 Ubuntu 目录：`/home/hnhyh/core_test`
- Java 服务运行在 WSL2 中
- MySQL 通过 Windows 宿主机 IP 访问：`172.25.224.1`
- Core 文件与测试程序通常位于同一目录或相邻目录
- 目标是打通以下闭环：

`WSL2 产生 core -> 自动扫描发现 -> 入库 -> 自动找到 ELF -> gdb 解析 -> 特征落库 -> 前端可见`

## 4. 原有代码中的关键问题

### 4.1 自动扫描与测试场景贴合不够
原始 `AutoScanService` 存在几个问题：

- 没有真正使用 `scan.enable`
- 不是递归扫描
- 文件刚生成时就可能立刻处理
- 自动扫描后复制到了存储目录，但原始路径丢失

### 4.2 程序路径推断不够贴近原始目录
`ProgramPathResolver` 原本主要基于：

- 当前存储后的路径
- 配置里的默认 `program-path`
- core 文件名推断 app 名称

问题在于：
自动扫描后，真正最可能找到 ELF 的原始目录信息丢失了，导致解析时只能围绕“存储副本目录”猜测。

### 4.3 状态可观测性不足
原先解析过程中，状态信息不够详细，难以定位：

- 原始文件来自哪里
- 存储后的路径是什么
- 最终用了哪个 `program-path`

这会显著增加联调成本。

## 5. 已完成的代码调整

### 5.1 `AutoScanService`
已做如下增强：

- 支持 `scan.enable`
- 支持递归扫描目录
- 增加文件稳定期判断，避免文件还在写入时被读取
- 跳过空文件和隐藏文件
- 自动扫描入库时，把原始来源路径记录下来

### 5.2 `DataParserService`
已增强解析时的过程记录：

- 记录原始 source 路径
- 记录平台存储路径
- 记录最终使用的 `program-path`

这样便于通过数据库状态快速判断自动识别逻辑是否正确。

### 5.3 `ProgramPathResolver`
已增强候选路径查找逻辑：

- 优先基于原始 source 目录寻找对应 ELF
- 兼容 stored 目录、configured program-path 的父目录及上级目录
- 保留基于 core 文件名推断程序名的逻辑

这更适合当前“core 和 ELF 都在 WSL2 测试目录里”的场景。

## 6. 当前阶段最推荐的测试策略

### 6.1 第一阶段：先做手工闭环
当前更推荐：

- 先不要依赖自动扫描验证全链路
- 先用手工上传或手工触发流程验证：
  - core 文件是否能被解析
  - program-path 是否能匹配到正确 ELF
  - `ParsedFeature` 是否能正常落库

原因：
自动扫描本身会引入额外变量，例如：

- 定时任务是否启动
- 扫描路径是否正确
- 文件是否满足稳定期要求
- 目录权限是否正确
- 文件名模式是否匹配

如果一上来把“扫描问题”和“解析问题”混在一起，很难快速定位。

### 6.2 第二阶段：再打开自动扫描
当手工闭环已经稳定后，再开启：

- `scan.enable: true`
- 在 `/home/hnhyh/core_test` 中生成新文件
- 观察数据库是否新增记录
- 观察状态是否从 `PENDING -> PARSING -> PARSED/FAILED`

## 7. 你现在“文件没被检测到”的最可能原因

如果你已经把 `scan.enable` 改成 `true`，但仍没有检测到，最常见原因有：

1. 服务没有重启
   - `@Value` 和配置不会热更新，改完 `application.yml` 后必须重启应用

2. 扫描周期未到
   - 当前 `scan.interval: 30000`，也就是 30 秒执行一次

3. 文件路径不在扫描目录内
   - 只会扫 `scan.coredump-paths: /home/hnhyh/core_test`
   - 日志只会扫 `scan.log-paths: /home/hnhyh/core_test/logs`

4. 文件名不匹配
   - core 要匹配 `core*`
   - log 要匹配 `*.log`

5. 文件刚生成，未满足稳定期
   - 当前代码会要求文件至少“稳定”几秒钟后才处理

6. 目录权限或运行位置不对
   - Java 进程必须真的运行在能访问 `/home/hnhyh/core_test` 的环境中

7. 你是在“本地手工调试解析”，但实际上并没有走到扫描链路
   - 这种情况下，开扫描并不能帮助定位解析问题，反而会增加干扰

---

## 8. 当前最实际的建议

### 如果你现在是在验证解析逻辑
建议：

- 可以暂时不依赖自动扫描
- 先通过手工方式确认：
  - core 文件本身有效
  - ELF 对应正确
  - gdb 能出调用栈
  - 解析结果能落库

### 如果你现在是在验证自动发现逻辑
建议：

- 打开自动扫描是有必要的
- 但要确认：
  - 服务已重启
  - 等待至少一个扫描周期
  - 文件路径、文件名、权限都符合要求

---

## 9. 下一步最值得继续做的事情

1. 给 `CoredumpFile` / `LogFile` 正式增加 `sourcePath` 字段
   - 不再复用 `errorMessage` 保存来源路径

2. 增加扫描日志
   - 明确打印：扫了哪个目录、发现多少文件、跳过原因是什么

3. 做第一版根因匹配服务
   - 基于 `crashSignal`、`callStack`、`errorKeywords` 等字段输出疑似根因

4. 视情况彻底移除旧解析器源码
   - 当前已不在界面和默认配置中使用 `LOCAL_GDB` / `REMOTE_SSH`
   - 如 WSL 工作树仍残留旧文件，可直接清理，避免编译混淆

5. 做最小可视化闭环
   - 调用栈
   - 线程信息
   - AI 诊断卡片

---

## 10. 总结

当前阶段最重要的不是同时验证“自动扫描 + 自动解析 + AI 分析 + 前端展示”，而是优先打通最小闭环。

更稳妥的顺序是：

1. 先手工验证解析链路
2. 再验证自动扫描是否稳定发现文件
3. 再补异常案例库与 AI 分析
4. 最后增强可视化表达

如果当前主要问题是“文件没有被检测到”，那么优先排查扫描链路；如果当前主要问题是“解析不成功”，那么可以暂时关闭自动扫描，先把解析链路单独跑通。
